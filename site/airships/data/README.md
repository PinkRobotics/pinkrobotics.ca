## Count correction

The earlier README said six files; it omitted the historical-fire dataset. It also described the
pre-regeneration Natural Earth vectors: 294 road polylines / 3,032 vertices and 23 outline rings /
804 vertices. Those historical values are retained here as the old values, not current measurements.
The table above is measured from the current files. `pipeline/vectors.py` now reproduces the vectors
from the pinned Natural Earth archive recorded in their sidecars. The notice repair changes no geometry.

Snapshot files are pinned test inputs. Re-fetching them changes the replay. This notice generator only
reads local bytes; it never calls an agency feed. Surface area is a proxy for water access, and simplified
historical perimeters are not operational fire lines. Providers do not endorse this project.

The wildfire records here come from public agencies under open licences. The separate
`exercise/` directory contains explicitly invented fires, never part of the season record. The fleet is simulated and never flew.

## The season files (`season/`)

`season/` is British Columbia's 2026 wildfire season as data, for a labelled replay of the
season on the monitor page. `pipeline/season.py` generates every file in it and opens no
network connection. It reads copies that already existed:

- one complete, unfiltered copy of the BC Wildfire Service's two public layers, incidents
  and perimeters, taken 2026-10-02T02:01:28Z, which is 19:01 on 1 October in British
  Columbia;
- the live mirror's own history: 113 dated copies each of `live/fires.json` and
  `live/perims.json` as this site served them between 9 August and 22 September 2026,
  recovered from the site's deploy history;
- `snapshot.json`.

The raw copies run to megabytes and are not in the repository. `season/2026.prov.json` names
each of them by sha256 and size.

| File | What it is |
|------|-----------|
| `season/2026.json` | One record per fire, as the public record stood when the copy was taken. **Hindsight in every field.** |
| `season/2026.summary.json` | The season's facts, computed: totals, the number of fires burning on each day, the peak, and the counts for each status day. Generated, never typed. |
| `season/2026.days.json` | The index of status days: the date, the kind of source, the time of the copy, counts, sha256. |
| `season/days/<date>/fires.json`, `perims.json` | A status day: what the public record said on that date, in the live mirror's own shape. |
| `season/2026.prov.json` | Provenance for all of the above in the sidecar convention, with every raw input and every output listed by sha256. |

### No lookahead

A fire's final size is hindsight. 1,144 of these 1,439 fires were under one hectare when
the copy was taken, and nobody knew that on the day each one started. A replay that sends
an imagined fleet to a fire because of what the fire later became has looked ahead.

So there are two kinds of file here, and they must not be mixed.

**`2026.json` is hindsight**: the size (the field is named `hindsightSizeHa` so that it
cannot be read as anything else), the status, the out date, and the ignition date as well.
The publisher goes on revising ignition dates after a fire is first reported: of the 232
fires that are in both this file and a status day, 119 carry a different ignition time than
on the first status day that listed them, 118 of those earlier, and for 66 the local date
itself moved. Nothing in `2026.json` may be given to the dispatch model. It says what the
season was.

**A status day is what was known.** The dispatch model may be shown a status day and
nothing else. On a date with no status day the fleet stands down, and the page says why.

The fires are real. The fleet is imagined and never flew. Nothing in these files says, and
nothing built on them may imply, that any fire would have burned differently.

### What a status day is

A status day is an America/Vancouver calendar date for which this project holds a dated
copy of the public record that it took itself. The files are the **last** copy of that
local date: every fire that was not out, with the status, size and ignition date the record
gave it at that moment, and the mapped perimeters.

| Date | Source | Copy taken (UTC) | Fires | Perimeters |
|------|--------|------------------|------:|-----------:|

| 2026-08-09 | mirror history | 2026-08-10T05:48:57Z | 103 | 75 |
| 2026-08-10 | mirror history | 2026-08-11T06:55:55Z | 101 | 74 |

The copy for 9 August was taken at 05:48 UTC on the 10th, which is 22:48 on the 9th in
British Columbia. The local date is the key, here and in the season file: the source stores
every date as epoch milliseconds in UTC, and each is converted with the America/Vancouver
time zone.

`fires.json` and `perims.json` have the document shape and the property names that
`pipeline/live.py` writes, `{fetchedAt, source, data}` with `data` a GeoJSON
FeatureCollection, so a status day can go through `normalize()` in `app/feeds.js` the way
a live feed does. There are three kinds of source:

- **mirror history**: a copy of the live mirror, kept byte for byte.
- **repository snapshot**: `snapshot.json`, with `FIRE_CENTRE` dropped from each fire and
  `FIRE_URL` from each perimeter, which leaves the mirror's property names.
- **capture**: a complete copy of both layers, filtered the way the mirror's request
  filters (`FIRE_STATUS <> 'Out'`, which in SQL also drops a missing status), with
  perimeters generalised to 0.002 degrees and four decimal places, as the mirror's request
  asks the server to do. The generalisation is done here. It gives the server's vertices
  exactly on every perimeter that a mirror copy or the snapshot holds at the same vintage
  as the capture, 97 of 97 and 24 of 24; `tests/season/check.py` proves that again
  whenever the raw inputs are present.

The table is every status day there is, out of the 217 dates from the season's first
recorded ignition to the capture. Between them the status days list 232 of the season's
1,439 fires. They also list V81619, on 14 August, which is the season file's V91619,
renumbered afterwards: the same sequence number, the same point, the same ignition time.
The other 1,207 fires of the season are on no status day. Each was out before the copy of
1 October was taken, and no dated record of it is held.

A status day is what the record showed, not everything that was burning. For 8 August the
season file now says 118 fires were burning at the moment of the copy; the copy listed 103
of them and not the other 15. `2026.summary.json` gives that comparison for every status
day.

### The shape of `2026.json`

A header, then `fires`: one record per line, sorted by the sequence number that ends the
fire number.

| Field | Meaning |
|-------|---------|
| `fire` | `FIRE_NUMBER`: a centre letter, a zone character and a province-wide sequence number. |
| `name`, `place` | `INCIDENT_NAME` and `GEOGRAPHIC_DESCRIPTION`, exactly as published. The name is often only the fire number and is sometimes null. |
| `lat`, `lon` | The layer's `LATITUDE` and `LONGITUDE`, four decimal places. |
| `centre` | The fire centre, by name. The layer publishes an integer code and no names; the names are this project's labels, keyed by the letter that begins the fire number. |
| `cause` | `FIRE_CAUSE`, the suspected cause. |
| `ignited`, `out` | **Timeline dates**: the local dates of `IGNITION_DATE` and `FIRE_OUT_DATE`. `out` is null for a fire that was not out. Both are null for a fire that is not on the timeline. |
| `statusAtCapture` | `FIRE_STATUS` when the copy was taken. |
| `fireOfNote`, `wasFireOfNote` | `FIRE_OF_NOTE_IND` and `WAS_FIRE_OF_NOTE_IND` when the copy was taken. |
| `hindsightSizeHa` | The layer's size estimate in hectares **when the copy was taken**. Never an input to anything that decides on a past day. |
| `ignitionMs`, `outMs` | `IGNITION_DATE` and `FIRE_OUT_DATE` exactly as published: epoch milliseconds, UTC. |
| `dates` | `{"ok": true}`, or what is wrong with the fire's dates and what was done about it. |

The header carries the capture time and the sha256 of each file of the capture, the layer,
`total`, `statusTally`, `impossibleDates` (the count a page should state), the notes, a
definition of every field, flag and rule, and the licence, attribution, non-endorsement and
not-for-emergency text.

There is no discovery date in the layer. `ignited` is the layer's ignition date, an
estimate the publisher revises; it is not the day a fire was found. A fire is counted as
burning on a day when `ignited <= day < out`: it was burning at the end of that day.

### Impossible dates

Ten of the 1,439 fires carry a date that cannot be true.

**An impossible date is never repaired and never dropped.** The fire stays in the file and
in every total. Its values stay exactly as published, in `ignitionMs`, `outMs` and
`dates.recorded`, and `dates.flags` says what is wrong. The fire is left off the day-by-day
timeline, with `ignited` and `out` both null, unless one of two rules places it.

A date is impossible when there is no ignition date; when the local year of the ignition
date is not the fire year the record gives; when the ignition or the out date is later than
the copy itself; when a fire that is out has no out date, or a fire that is not out has one;
when the fire is out before it ignited; or when a status day lists the fire at a time
earlier than its ignition date. Four of those eight tests find something in 2026.

The two rules that place a flagged fire:

- **`dated-record`**. The ignition date at capture is impossible, the out date is not in
  question, and every status day that lists the fire gives one and the same ignition date,
  which is possible. The fire is placed from that date.
- **`same-local-day`**. The only fault is an out time earlier than the ignition time, and
  both fall on one local date. The timeline is kept by date, so the fire starts and is out
  on that date and is burning at the end of no day.

Nothing is placed by inference. Fire numbers end in a sequence number that follows the
calendar closely and not exactly: taking the fires with possible dates in number order,
1,076 of 1,428 ignited within a day of the fire numbered before them, and the widest gap is
72 days. So the fires numbered either side of a flagged fire are evidence of when it
entered the record, and `dates.bracket` names them. They are never used to place it.

What the evidence supports, fire by fire. Three fires have an ignition in 2025, which could
be a year typed wrong or a real fire held over from the year before:

- **V30852** is a year typed wrong, and the record proves it. Six status days, 8 to 13
  August, give its ignition as 2026-07-15T23:04:06Z. The value was revised after that and
  the year went wrong in the revision. Placed from 15 July by `dated-record`.
- **G90400** is most likely a year typed wrong: the fires numbered either side of it ignited
  on 20 and 22 May 2026, and its recorded date is 20 May. But the seven status days that
  list it, 8 to 14 August, all carry the 2025 value. No record says 2026, and a fire held
  over from 2025 cannot be ruled out. Not placed.
- **G40517** is not a year typed wrong: 1 October 2026 is months after it was out. The
  fires numbered either side ignited on 5 and 6 June 2026 and it was out on 7 June. That
  fits a fire lit in the autumn of 2025 and found the next June, a holdover. It also fits a
  date entered wrong in some other way. The layer has no discovery date and the record does
  not say which. Not placed.

The other seven:

- **K41895**: midnight on 22 August 2001. The fires numbered either side ignited on 22 and
  23 August 2026 and it was out on 24 August, so the year is most likely wrong and the day
  right. No status day lists it and nothing confirms that. Not placed.
- **V10408**: midnight on 1 January 1900, on a clock seven hours behind UTC. That reads as
  a placeholder for a date nobody entered. There is no date to recover. Not placed.
- **C20940**, in December 1429, and **C30602**, in December 2044, are not dates anybody
  meant. No status day lists either fire. Not placed.
- **V10591**: out 26 minutes before an ignition time given to the exact hour, both on
  19 June. Placed on 19 June by `same-local-day`. Which of the two times is wrong is not
  decided.
- **N52060**: ignited on 27 September, out on 6 September. The fires numbered either side
  ignited on 26 and 27 August, which fits an ignition on 27 August with the month typed
  wrong, and fits other errors too. No status day lists it. Not placed.
- **K61758** was not out when the copy was taken. The status day of 20 September lists it
  two days before the ignition date it carries, 22 September, and carries that same date.
  Its number sits among fires of 22 August, so the month is most likely wrong, and no
  record gives another date. It is not placed on the timeline. It is in every status day
  that lists it, exactly as the record showed it.

The status-day files keep their own impossible values untouched as well; `2026.days.json`
lists them for each day under `impossibleAsKnown`.

The flags mark what cannot be true, not what looks unlikely. The lowest-numbered fire
ignited on 1 April. Five fires have an ignition date earlier than that, and two of them,
G70141 and G40209, are numbered among fires that started a month or more later. A fire can
burn for weeks before it is found, so those dates are possible, and they are used as
recorded. The timeline begins on 27 February because one of the five is recorded as
igniting that day.

One limit of the year test: it goes by calendar year. Numbering that starts on 1 April
suggests a fire year that runs from April to March. If so, a copy taken after 31 December
would need the test widened before a January ignition is called impossible.

### Regenerating and checking

```
python3 pipeline/season.py <capture folder>                        # regenerate, and print the impossible-date table
python3 pipeline/season.py <capture folder> --through 2026-10-02   # the same, adding later captures as status days
python3 pipeline/season.py --check                                 # the gate: needs no raw inputs
make seasoncheck                                                   # the gate, the pinned totals, the policy tests
SEASON_CAPTURE=<capture folder> make seasoncheck                   # and a regeneration from the raw inputs, byte for byte
```

A capture folder is named by its local date and holds a `MANIFEST.json` listing each file
with its sha256, the layers' own counts and `complete: true`; nothing in it is believed
until every file matches. Later captures sit beside it as sibling folders. The mirror
history is looked for at `../../mirror-history` from the capture folder, or where
`--mirror-history` says. `--through` adds every complete sibling capture up to that date as
a status day and leaves the season record pinned to its own capture. Pointing the command at
a newer capture folder re-pins the season record instead, and the totals above move.
The provenance sidecar records every capture folder used and a digest of all its files,
including superseded captures. Raw checks use exactly those folders: additional captures
are named as information and ignored; a missing or changed recorded folder fails.
Regeneration without `--check` deliberately adopts eligible new captures.

What `--check` can prove without the raw inputs: that every derived value (the local dates,
the flags, the placements, the summary, the index, the provenance) is what the generator
makes from the published values in the committed files; that the mirror-history days
still have the sha256 recorded for the recovered copies; and that the day of 8 August is
`snapshot.json`. What it cannot prove is that those published values and sha256s are the
raw inputs', because the checker does not have them. `tests/season/check.py` pins a
fingerprint of both for that reason, and with `SEASON_CAPTURE` set it regenerates
everything from the raw inputs and compares bytes.

### The guard file

`2026.guard.json` is the one file in `season/` that no pipeline writes: a ruling about the
replay, carried as data rather than code so that widening a window or softening a distance
is an edit anyone can see. A test pins its canonical digest, which makes that edit a
deliberate two-place change. It names the days no fleet is simulated for, the fires the
simulated fleet never works, and the keep-out distances kept around them; `sim/guard.js`
reads it and the monitor obeys it on every view.

| | |
|---|---|
| No-fleet window | 2026-08-08 to 2026-08-27, the provincial state of emergency |
| Fires the fleet never works | 22 — 8 in tier 1 (loss), 7 in tier 2 (evacuation order), 7 in tier 3 (alert, or first discovered near people) |
| Keep-out distance | 25 km around tiers 1 and 2, and by default; 0 around tier 3 |
| Places kept clear | 2, each on its own date |

The tier says why a fire is listed, and the distance follows the reason: a fire tied to a
loss or an evacuation order gets 25 km of clear air; a fire that only carried an alert, or
was first discovered near people, is never worked but claims no ring beyond its own
outline. The list is not the whole rule. Any fire flagged a wildfire of note in the day's
own data is held the same way, listed or not — at the default distance when the list has
no entry for it — and so is any fire the season record marks `fireOfNote` or
`wasFireOfNote`. If the guard file cannot be read, or a day's own files fail their checks,
the fleet stands down for that view and the page says so in words; it never flies anyway.

Every entry carries exactly one source link to the public reporting it rests on;
`2026.guard.prov.json` records the rest. The file quotes nothing and names nobody: it
belongs to a page that does not replay those days with a different ending.

### The evacuation record

`2026.evac.json` is the guard's other half of "led to an evacuation order or alert": the
fires that ever were, by fire number, as data reduced from captured days of the province's
public evacuation orders and alerts layer — not the hand list, and never typed. Generated
by `pipeline/season.py --evac <capture folder>`; `--check` recomputes it from committed
files, `make evaccheck` regenerates it byte for byte (from `tests/evac/fixtures/` without
the raw inputs, from `inputs/evac-capture/` when the raw capture is present).

| | |
|---|---|
| Captured days | 1 — 2026-10-02, taken at 2026-10-02T07:08:47Z (16 features) |
| Fire events | 10, on 6 fire numbers (5 order features, 5 alert features, 0 orders with no geometry) |
| Ever under an order | 4 fires |
| Ever under an alert of any kind | 3 fires |
| Order outlines | 55, simplified to 0.002 degrees, each ring its own patch |
| Other event types | counted in the sidecar, otherwise left out (2 Flood, 4 Landslide) |

Two halves to read before using a value. **Ever**, not now: a fire under an order on any
captured day carries `everOrder` true for good, because the layer moves fires out when
orders are rescinded and this record keeps what the captured days showed. And **minimal
fields**: number, order/alert, first and last captured day, order outlines — the layer's
counts of homes and population, the issuing agency and every free-text name are dropped on
the way in and appear in no file this project carries; `tests/evac/check.py` refuses them
anywhere in the tracked tree.

The guard reads it beside the hand list, and the stricter of the two always wins: a fire
the data holds that the hand list does not is held anyway, an order tightens a hand entry
to the default distance and never loosens one, and a tie keeps the hand entry's own tier.
An order area is itself a keep-out region for every simulated position and path, in
addition to the fire's own. As of this capture every fire in the data is already on the
hand list at the default distance, so the applied tiers are unchanged — the record's work
today is holding that true as orders change. A malformed record stands the fleet down in
words, exactly as an unreadable guard file does. Open Government Licence - British Columbia. Rescinded orders leave this current layer for a historical dataset, so a season built from this layer is incomplete by construction.
